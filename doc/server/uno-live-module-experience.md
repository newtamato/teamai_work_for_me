# UNO 直播模块实现经验

> 实现说明 / 测试记录
>
> 本文总结 GAM-6 第一版本的服务端实现方式、联调方法和已知边界，供后续 agent 开发其他玩法直播功能时参考。当前代码和 `doc/UNO_PROJECT_SPEC.md` 仍是最终事实来源。

## 1. 总体原则

直播是游戏桌的附属能力，不要为直播再创建一套游戏房间。游戏桌负责产生权威牌局状态，直播模块负责把状态转换成通用直播消息并转发给观众。

UNO 与 Carrom 的业务逻辑应分开：

- UNO 直播入口放在独立的 `uno_live/` 模块中。
- 可以复用通用的 Live、LiveChat、观众连接和礼物基础设施。
- 不要直接复用 Carrom 的牌局解析、支付、促销、横幅或社交埋点逻辑。
- 直播协议应描述桌子、观众、礼物、聊天和牌局事件，不应把 Carrom 或 UNO 的业务字段写进通用协议；玩法专属状态放入对应玩法自己的 payload。

## 2. 服务链路

当前验证过的链路如下：

```text
UNO GameTable
  -> NotifyLive()
  -> caiilivesvr 的 UNO 直播模块
  -> LiveBout / LiveChat
  -> 观众连接
```

直播列表不是由游戏服直接提供。测试流程是：

```text
客户端/测试程序
  -> Assist 查询直播列表
  -> 根据返回的 bout/live 信息连接 Live 服务
  -> EnterLive
  -> 加入 LiveChat
```

需要区分：

- Assist MP：负责查询入口和业务请求。
- Live 服务：负责观众进入直播、直播事件和聊天链路。
- Live MP：是服务间或 MP 入口，不一定接受测试客户端的直接长连接。
- Chunk：负责部分跨服务业务，例如礼物请求转发；它不是直播观战连接地址。

## 3. UNO 开局与直播桌

第一版本采用最简单策略：UNO 牌局开局后自动成为直播桌，`CanLive()` 直接返回 `true`。后续如果需要按房间、等级、隐私或运营开关控制，再把判断下沉到统一配置或策略函数。

直播房主不再固定使用 1 号座位。开局时：

1. 收集桌上的真人玩家。
2. 从真人玩家中随机选择 `live_master_userid_`。
3. 后续直播状态和房主牌面都使用这个 userid。

不能把“找到一个 `masterid`”当成完成。必须确认它真正写入桌子的直播房主字段，例如执行对应的 `set_master_userid` 流程，否则列表或直播状态会出现房主为空/错误的问题。

## 4. 事件和可见性

玩家与观众不是同一种接收者，必须在发送处区分：

| 接收者 | 允许的内容 |
|---|---|
| 对战玩家 | 公共桌面状态、自己的完整手牌、回合和动作事件 |
| 观众 | 公共桌面状态、展示动画所需的动作/回合事件、房主允许展示的牌面 |

关键区别：

- `GN_C_UNO_HAND_UPDATE` 是玩家私有手牌通知，不应作为观众牌局状态的判断依据。
- `GN_C_UNO_TABLE_STATE` 是观众观看牌局的主要公共状态通知。
- 出牌、摸牌、回合变化和结算等通知可以发送给直播链路，让观众播放完整牌局过程。
- 如果产品要求观众回看房主手牌，应在 UNO 直播 payload 中明确表达，不能误把普通玩家的私有手牌广播给所有接收者。

实现时建议沿用以下顺序：

```text
更新 UNO 状态
  -> 给玩家发送私有 HandUpdate
  -> 给玩家和直播发送公共 TableState
  -> 给玩家和直播发送动作/回合事件
  -> 结算时发送 GameResult
```

## 5. 直播列表

UNO 直播列表第一版本不在服务端做排序，也不应沿用 Carrom 的最多 20 张限制。服务端应返回足够的原始数据，由客户端排序和展示，至少包括：

- `heat_value`
- `game_start_time`
- `audience_count`
- `bout_id`
- `live_master_userid`
- 客户端建立连接所需的直播地址或入口信息

列表字段可以使用通用直播字段；UNO 专属字段应放在 UNO 扩展数据中，避免污染 Carrom 或公共协议。

## 6. 观众生命周期

观众进入后必须保持在直播连接中，直到牌局收到 `GN_C_UNO_GAME_RESULT`，或服务端明确发送直播结束事件。测试程序如果在聊天后立即退出，会制造“观众断线”的假象，掩盖真实的牌局事件链路。

正常流程：

```text
Assist 获取列表
  -> EnterLive
  -> 加入 LiveChat
  -> 接收 TableState / PlayCard / DrawCard / TurnChanged
  -> 接收 GameResult
  -> 服务端清理直播桌和观众
```

观众断线时发送或处理 `GR_LIVE_AUDIENCE_CHANGE`，只更新观众数量和直播状态，不影响 UNO 牌局。牌局结束后再统一解除直播桌、清理 LiveBout/LiveChat 数据。

## 7. 聊天和礼物

聊天应复用通用 LiveChat，但玩家集合和直播 bout 必须由 UNO 牌局正确创建、销毁和关联。聊天频道中可以同时存在对战玩家和观众。

礼物链路应保持玩法隔离：

```text
UNO Gift Request
  -> caiichunksvr UNO gift module
  -> live gift notification
  -> UNO LiveChat
  -> player gift notification
```

关键字段：

- `bout_id`：定位 UNO 的 LiveBout/LiveChat。
- `to_userid`：礼物目标必须是牌局玩家。
- `to_robot`：保留机器人收礼路径需要的标记。
- `req_guid`：用于请求幂等和日志关联。

观众可以给参赛玩家送礼，不能给观众送礼。Carrom 的免费礼物、促销、联盟和横幅逻辑不能因为复用代码而自动进入 UNO。

## 8. 联调测试经验

最小有效测试是三个用户：

1. 用户 1、2 进入同一 UNO 桌并开始对战。
2. 用户 3 从 Assist 直播列表找到该桌。
3. 用户 3 通过实际 Live 服务进入观战。
4. 三人加入同一聊天频道并互相发送聊天消息。
5. 让用户 1、2 继续完成牌局。
6. 确认用户 3 在结算前没有离开，并收到牌局事件和 `GN_C_UNO_GAME_RESULT`。

测试日志至少打印：

- 请求名、userid、bout_id、request id。
- EnterLive 成功/失败及返回码。
- 每个收到的事件号和 payload 长度。
- `TABLE_STATE`、动作通知、回合变化、结算通知。
- Audience enter/quit 和聊天收发结果。

本次验证确认观众收到了出牌、摸牌、回合变化和结算事件；`HAND_UPDATE` 只用于玩家手牌，不作为观众验证项。

## 9. 已知坑和后续检查

- 列表返回的 Live MP 地址与测试客户端实际可连接的 Live 服务端口可能不同。当前环境验证使用 `4580`；`4581` 是 MP 入口，不能默认当作客户端长连接地址。正式客户端使用前必须统一服务端广告地址。
- 只看到 `NotifyLive()` 被调用，不代表观众已收到消息；必须从 caiisvr、livesvr 和测试客户端三端日志交叉确认。
- 只测试 EnterLive 后立即退出，会误判观众生命周期。必须等待结算事件。
- 直播 payload 中出现玩家 `private_state` 时，要重新检查接收者范围，避免把非房主手牌或普通玩家私有数据泄露给错误接收者。
- 变更 `GameTable`、`GameBoutData` 等公共生命周期时要回归 UNO，因为 UNO 虽然已剥离 Carrom 业务，但仍依赖部分公共生命周期。

- [ ] 发送通用直播字段和玩法专属公共状态。
- [ ] 区分玩家私有通知与观众公共通知。
- [ ] 接入观众进入、退出和 `GR_LIVE_AUDIENCE_CHANGE`。
- [ ] 接入同频道聊天。
- [ ] 接入只面向参赛玩家的礼物目标校验。
- [ ] 牌局结束后清理直播状态。
- [ ] 用“两名玩家 + 一名观众”跑完整牌局，而不是只验证连接成功。
